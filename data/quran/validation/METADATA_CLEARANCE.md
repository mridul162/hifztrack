## Madani 1441H verification

- The KFGQPC publisher lists SHA-256 `c2fa8d93a7c4f689b58eb32756e1ae56cd1b7ce4826f63e09723be8b092224fb` for its 1441H printing artwork. The artwork-based comparison uses Quran.ws's published extraction. The exporter derives its indexes from the pages and identifies its pipeline commit `26d71e3` and artwork commit `3ff27b46`. The same project's rendering provenance identifies those printed plates as Madani V4, 1441H, Hafs. This review used the indexed extraction and independently compared every range against the KFGQPC developer archive (v2.0, update 13.0) and QUL's 1441H page list. [KFGQPC master](https://qurancomplex.gov.sa/mushaf-printing) · [1441H artwork provenance](https://png.quran.ws/about/) · [Exporter methodology](https://quran.ws/docs/reference/quran-svg-elements/) · [Pinned release](https://github.com/quran-ws/quran-svg-elements/releases/tag/v1.1.1) · [QUL ranges](https://qul.tarteel.ai/mushaf_layouts/19)
- The release manifest checksum for the exact numeric index is `43d1d7ebaf009340d943a4d43bcbddfedd2c649a8410a37ee276cb7f7520d60c`. The normalized UTF-8 LF file has SHA-256 `0122616bcfd941438344ea8cb46420f79ef32c75de53c921ecc269c07e10da3a`. The per-file rights statement covers the exporter-created indexes. Its attribution waiver covers in-product uses, and HifzTrack includes full credit because the numeric ranges are redistributed. KFGQPC's developer data, printed artwork, and Quran verse text were used or identified as evidence under their respective terms. The derivative consists of numeric range fields. [Release manifest](https://cdn.quran.ws/svg/elements/v1.1.1/manifest.json) · [Quran.ws rights policy](https://quran.ws/docs/guidelines/licensing/) · [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)
- All 604 pages are sequential and cover the numbered Ayahs exactly once, with 54 cross-Surah ranges. Page 48 contains only `2:282`. Page 604 spans `112:1` through `114:6`. The 1441H ranges use numbered Ayahs, so physical headers and unnumbered Basmala lines introduce no extra coordinates. The validation found no page split requiring a second page reference for the same numbered Ayah.
- The QURAN-01B write-up counted **24** changed starts. The enumerated comparison contains **25** changed starts and **36** changed ranges versus the 1405H table. The corrected start list is `121, 122, 123, 145, 532, 533, 534, 565, 568, 570, 576, 584, 586, 588, 589, 590, 592, 593, 594, 595, 596, 597, 598, 599, 600`. ## Implementation and verification

From `backend/`, `python -m app.quran.import_reference --with-pages` loads the approved page data alongside the numeric reference in a single transaction. It also extends an existing matching numeric import. It verifies the pinned file checksum, full coverage and declared endpoints and rejects partial or conflicting stored page data. It uses `quran_pages` and the `MUSHAF_PAGES` provenance record. The importer and page finder operate on canonical coordinates. The frontend uses those coordinates in the existing Sabaq and revision forms. [API contracts](../../../docs/architecture/API_SPECIFICATION.md) · [Database design](../../../docs/architecture/DATABASE_DESIGN.md) · [UI behavior](../../../docs/user-experience/UI_REQUIREMENTS.md)

To reproduce the source comparison, save [the manifest](https://cdn.quran.ws/svg/elements/v1.1.1/manifest.json) as `manifest.json` and [the numeric index](https://cdn.quran.ws/svg/elements/v1.1.1/index/pages.json) as `pages.json` with `kfgqpc-archive.zip`, `qul-v1.html` and `qul-v4.html` from the readiness report. From the repository root, run:

```powershell
python -B data/quran/validation/verify_madani_pages.py <evidence-directory>
```

The full guarded PostgreSQL 18.6 backend suite passed with **110 tests and zero skips**. `python -m alembic upgrade head` reached `0008_group_sharing` on a fresh disposable database and `python -m alembic check` found no drift. `python -m pytest -q -p no:cacheprovider --basetemp <disposable-directory>` exercised exact API range agreement, inverse lookup and invalid references, idempotence, unavailable and partial imports, transaction rollback, and preserved personal histories, sharing settings and dashboard responses. The two dataset validation tests passed with `python -m pytest -q data/quran/validation/test_validate_datasets.py`. `node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json`, `node node_modules/next/dist/bin/next build --webpack`, and `docker compose --env-file .env.example -f infrastructure/docker/compose.yaml config --quiet` also passed. PostgreSQL 17, pinned by Compose, remains unverified because only 18.6 was installed and the Docker daemon was unavailable.

Headless Chrome verified numeric fallback before import, the 604 options and edition label after refresh, the page 120 boundary, the cross-Surah page 604 range, successful Sabaq and revision saves using that range, and a page-based Sabaq correction that preserved the original record. It also verified the picker loading and error messages and continued numeric browsing when the page API fails. Imports and browser writes ran on disposable databases.
